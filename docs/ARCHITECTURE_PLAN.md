# План миграции: одностраничный HTML → Next.js

## Почему Next.js (коротко)

- **App Router + Server Components** — данные тянутся на сервере при
  генерации страницы, значит поисковик (и просто "curl" без JS) видит
  готовый HTML с именами игроков и счётом, а не пустой `<div id="app">`.
- **Серверный fetch не подчиняется CORS.** Все костыли с "каким доменом
  можно, каким нельзя" (см. `API_REFERENCE.md` §0) становятся неважны —
  сервер бьёт напрямую в любой домен WTT.
- Встроенный ISR (Incremental Static Regeneration) — статическая страница,
  которая тихо перегенерируется раз в N секунд, идеально ложится на
  "показываем расписание турнира, обновляем раз в 30 сек".
- Готовая экосистема деплоя (Vercel) с доменом, аналитикой, edge-кэшем
  из коробки — меньше своей инфраструктуры собирать руками.

Альтернативы, если Next.js не зайдёт: **Astro** (ещё более SEO-заточен,
"islands" — минимум JS на клиенте) или **SvelteKit**. Ниже план дан под
Next.js, но структура (роуты, слой данных, ISR) переносится почти 1:1.

## Слой данных: где именно живёт вся логика из прототипа

Вся логика в `prototype/wtt-matches.html` (парсинг, дедуп, слияние
источников, вычисление статуса по счёту, паддинг `documentCode`) уже
написана, проверена на реальных данных и обкатана на живых багах WTT.
**Не переписывать с нуля** — перенести функции как есть в `lib/wtt-api.ts`
и `lib/merge-matches.ts`, только заменить `fetch()` в браузере на
`fetch()` внутри Server Component / Route Handler (сигнатура та же).

Ключевые функции для переноса (ищи в прототипе по имени):
- `dedupeUnits`, `buildMatch`, `buildMatchFromArchiveItem`,
  `buildOrphanLiveMatch`, `computeMergedMatches`, `hasRealPlayers`,
  `fullDocCode`, `normalizeCode`, `parseScores`.

## Стратегия рендеринга и обновления данных

Данные турнира устроены неоднородно по "скорости изменения":

| Что | Как часто меняется | Стратегия |
|---|---|---|
| Список турниров | Раз в дни | ISR, revalidate ~ 1 час |
| Расписание турнира (предстоящие/завершённые) | Раз в минуты (в разгар турнира) | ISR, revalidate ~ 30–60 сек, **plus** клиентский polling поверх для live-секции |
| Счёт live-матча | Каждые несколько очков | Клиентский polling (Client Component с `useEffect`+`setInterval`, как в прототипе) поверх серверно отрендеренной оболочки |

Практический паттерн: страница турнира — Server Component (даёт SEO,
быстрый первый рендер), а внутри — маленький Client Component
`<LiveScoreUpdater>`, который на клиенте поверх готовой разметки
подтягивает live-счёт каждые 30 сек (логика уже есть в прототипе —
`fetchLiveScores`/`fillMissingScores`). Поисковик видит статичный снимок,
живой пользователь — обновляющийся.

## SEO-специфика

- `generateMetadata` на странице турнира — заголовок вида
  "WTT Contender Panagyurishte 2026 — расписание и результаты".
- JSON-LD `SportsEvent`/`SportsTeam` разметка на странице (см.
  `docs/SEO_AND_ANALYTICS.md`).
- `generateStaticParams` для уже известных `eventId` — предгенерировать
  топ-N активных/ближайших турниров статически при сборке, остальное —
  ISR по требованию (`dynamicParams: true`).

## Кэш на клиенте (IndexedDB) — что с ним делать

Логика "никогда не перезапрашивать уже известный счёт завершённого
матча" (см. `KNOWN_ISSUES.md` — это явное требование пользователя,
уже реализовано в прототипе через IndexedDB) остаётся актуальной и в
Next.js-версии **как дополнительный клиентский слой** поверх серверного
ISR — она защищает от лишних точечных догрузок (`matchdata/`) на
клиенте при скролле/фильтрации, ISR же экономит нагрузку на сам
переход между страницами. Переносится как есть (IndexedDB — браузерный
API, не зависит от фреймворка).

## Порядок работ (рекомендуемая последовательность)

1. Скаффолдинг `create-next-app` (TypeScript, App Router, Tailwind —
   в прототипе уже свой дизайн-язык на CSS-переменных, можно перенести
   один в один в `globals.css` без реальной миграции на Tailwind).
2. Перенести `lib/wtt-api.ts` + `lib/merge-matches.ts` дословно из
   прототипа, обернуть в Server Actions / Route Handlers.
3. Собрать страницу турнира как Server Component, без фильтров/live-
   поллинга — убедиться, что SSR HTML содержит реальные карточки
   (`view-source:` должен показывать имена игроков).
4. Добавить Client Components: фильтры, live-polling, тема, зум-слайдер.
5. `docs/SEO_AND_ANALYTICS.md` → метатеги, sitemap, аналитика.
6. Деплой на Vercel + свой домен.
