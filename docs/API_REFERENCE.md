# WTT API Reference (реверс-инжиниринг)

Всё найдено вручную через анализ сетевых запросов и минифицированного
Angular-бандла worldtabletennis.com. Официальной документации не существует —
это неофициальный, недокументированный API. Всё ниже актуально на момент
этой сессии (сентябрь 2026); может измениться без предупреждения.

## 0. Домены и CORS — читай это первым

WTT раздаёт одни и те же данные через несколько зеркал (Azure Front Door)
с **разными правилами CORS**:

| Домен | CORS с чужого origin | Использовать? |
|---|---|---|
| `wtt-web-frontdoor-cthahjeqhbh6aqe3.a01.azurefd.net` | ✅ Открыт (`Access-Control-Allow-Origin` разрешает любой origin) | **Да, основной домен для клиентского fetch** |
| `wtt-web-frontdoor-withoutcache-cqakg0andqf5hchn.a01.azurefd.net` | ❌ Закрыт (`Failed to fetch` с чужого домена) | Только same-origin (сам сайт WTT) |
| `wtt-website-api-vm-frontdoor-hhaec5epbhdyfugz.a01.azurefd.net` | ⚠️ Частично — проверяет Origin/Referer на уровне приложения, чужим доменам отдаёт 400/422 | Не использовать для клиентского fetch |

**Важно:** это ограничение исчезает полностью, если делать запросы с
**сервера** (Next.js Route Handler / Server Component) — CORS действует
только в браузере. Так что при переезде на Next.js можно спокойно
стучаться в ЛЮБОЙ из доменов выше, включая закрытые для браузера.

Все пути ниже даны относительно открытого домена
`wtt-web-frontdoor-cthahjeqhbh6aqe3.a01.azurefd.net`, если не сказано иное.

## 1. Список турниров

```
GET /websitestaticapifiles/general/wtt_upcoming_only_events_list.json
```

Несмотря на название — это **полный** список турниров (проверено: 484 шт.,
из них 447 прошедших, 34 будущих, 3 идущих на момент проверки), не только
будущих. Даёт `eventId`, `eventName`, `startDateTime`, `endDateTime`.
Статус турнира (идёт/будущий/прошедший) выводится сравнением этих дат с
текущим временем — сервер такого поля не даёт.

Есть также более старый список:
```
GET /websitestaticapifiles/general/wtt_event_subevent_dropdown_list.json
```
Даёт `eventId` + `subEventType` + `eventName`, но **один эвент повторяется
по разу на каждый sub-event** (Men's Singles, Women's Singles, ...) — нужно
дедуплицировать по `eventId`. Не даёт дат. Используй первый список вместо
этого, если нужны даты/статус.

## 2. Расписание/матчи турнира — САМОЕ ВАЖНОЕ, ЧИТАЙ ВНИМАТЕЛЬНО

```
GET /websitecacheddata/{eventId}/schedule/schedule.json
```

### ⚠️ КРИТИЧЕСКИЙ БАГ, на который ушло полсессии

Ответ — массив объектов вида `{ "Competition": { "Unit": [...] } }`.

**`Unit` — это МАССИВ, и в нём может быть от 1 до 30+ матчей одновременно**,
не один матч! Мы всю сессию писали `item.Competition.Unit[0]` (взять первый
матч) и тем самым **отбрасывали остальные** — вот откуда была вся путаница
с "почему только 1 будущий матч, хотя на сайте их 27".

**Правильно:**
```js
const allUnits = [];
scheduleRaw.forEach(item => {
  (item.Competition.Unit || []).forEach(u => allUnits.push(u));
});
```
**Неправильно (баг):**
```js
const units = scheduleRaw.map(item => item.Competition.Unit[0]); // теряет данные!
```

### Дедупликация

Один и тот же матч (`Code`) может встречаться в ответе **несколько раз** с
разными `ScheduleStatus` (устаревшие снапшоты вперемешку со свежими —
баг/особенность бэкенда WTT, не наша). Дедуплицировать по `Code` (без
хвостовых дефисов, см. ниже), оставляя запись с самым "продвинутым"
статусом:

```
Official (3) > Start List (2) > Scheduled (1)
```

### Поля одного `Unit`

| Поле | Что | Примечание |
|---|---|---|
| `Code` | Код матча | **Короче** полного `documentCode` ровно на 8 символов (см. §5) |
| `ScheduleStatus` | `Scheduled` \| `Start List` (live) \| `Official` (завершён) | Может **отставать от реальности** — см. ниже |
| `StartDate` / `EndDate` | Время | Локальное время площадки, без явной таймзоны в строке |
| `StartList.Start[]` | Игроки | `Start[].Competitor.Description.TeamName` — имя. Если **пусто/`null`** — это TBD-слот сетки (соперник ещё не определён по итогам предыдущего раунда), не показывать как обычный матч |
| `Round`, `SubEvent`, `ItemDescription[0].Value` | Раунд/тип | `ItemDescription[0].Value` обычно самое читаемое ("Women's Singles - Round of 32 - Match 1") |
| `VenueDescription.LocationName` | Стол | "Table 1" |
| `VenueDescription.VenueName` | Площадка | |

### `ScheduleStatus` может врать — доверяй счёту

На практике находили матчи, у которых `ScheduleStatus` неделями оставался
`Start List` (как будто матч всё ещё идёт), хотя счёт (см. §4/§6) уже
показывал явного победителя. **Всегда пересчитывай статус из самого счёта**:
если по счёту у одной из сторон набрано ⌈bestOfXGames/2⌉ выигранных геймов —
матч завершён, даже если `ScheduleStatus` говорит другое.

### Live-матчи, которых вообще нет в `schedule.json`

Отдельно найдено: `schedule.json` может **полностью не содержать** матч,
который в этот момент реально идёт (подтверждено вживую: 4 матча были в
`livematchids.json` — см. §3 — но отсутствовали в `schedule.json` целиком).
Поэтому live-статус нельзя определять только по `schedule.json` — обязательно
сверяться с `livematchids.json`, и если код оттуда не находится в расписании,
дотягивать карточку через `matchdata/` (§5) напрямую.

### `schedule_filtered.json` — не то, что кажется

```
GET /websitecacheddata/{eventId}/schedule/schedule_filtered.json
```
Существует, но отдаёт **не** "все предстоящие" — маленькую произвольную
подвыборку (в тесте — 5 записей). Судя по всему, используется для какого-то
другого виджета на сайте, не для вкладки Matches. Не полагаться на него как
на основной источник.

## 3. Live-матчи (ID)

```
GET /websitestaticapifiles/running-events/{eventId}/{eventId}_livematchids.json
```

Короткий JSON `[{"e":"{eventId}","d":"{documentCode}","s":"{subEventName}"}]`
— список матчей, которые **live прямо сейчас**. `d` — уже полный
`documentCode` (готов к использованию в `matchdata/`, паддинг не нужен).

Обновляется быстрее и полнее, чем `ScheduleStatus` внутри `schedule.json`
(см. предупреждение в §2). Может на несколько секунд отставать и в
обратную сторону — матч уже закончился, а тут ещё числится live; поэтому и
здесь стоит перепроверять по факту счёта (§6).

## 4. Результаты — три РАЗНЫХ источника для разных случаев

### 4a. Последние 10 результатов активного турнира (со счётом)

```
GET /websitestaticapifiles/{eventId}/{eventId}_take_10_official_results.json
```
Полные карточки (`match_card`, включая счёт) — но **только для последних
10** завершённых матчей турнира в целом (не по под-событию — по всему
турниру!). На турнирах с групповым этапом (много параллельных матчей) это
исчерпывается очень быстро.

### 4b. Полный список результатов активного турнира (БЕЗ счёта)

```
GET /websitecacheddata/{eventId}/officialresult/officialresult.json
```
Все завершённые матчи турнира, но `match_card` внутри — **всегда `null`**
для ещё идущего турнира. Полезен только чтобы узнать, какие матчи вообще
завершены (список `documentCode`), не для счёта.

Есть более компактный вариант с тем же списком:
```
GET /websitecacheddata/{eventId}/officialresult/officialresult_minimal.json
```

### 4c. Архив — полная история СО СЧЁТОМ, но только для давно завершённых турниров

```
GET /websitearchivedresults/{eventId}/officialresult/officialresult.json
```
Для турнира, который завершился достаточно давно (и WTT успел его
заархивировать) — это ЕДИНСТВЕННЫЙ источник с **полной** историей матчей,
причём каждый элемент уже содержит целиком заполненный `match_card` (счёт,
игроки, стол, раунд — как из `matchdata/`, см. §5). Для АКТИВНОГО турнира
этот путь отдаёт **404** — используй 4a/4b + точечную дозагрузку (§5)
вместо него.

**Стратегия:** пробовать архив первым; если 404/пусто — считать турнир
активным и собирать данные из 2 + 4a + точечных догрузок 5 для недостающих
завершённых матчей.

## 5. Карточка одного матча (точечно, по коду)

```
GET /matchdata/{eventId}/{documentCode}.json
```

Полная карточка: `subEventDescription`, `tableNumber`/`tableName`,
`venueName`, `matchConfig.bestOfXGames`, `competitiors[]` (имя + `scores`,
строка вида `"11,7,11,9,6"` — по одному числу на гейм, для каждого из двух
игроков/пар отдельно).

`documentCode` **фиксированной длины 42 символа**. Значение `Code` из
`schedule.json` короче ровно на 8 символов — просто дополни дефисами до 42:

```js
function fullDocCode(code) {
  return code.length >= 42 ? code : code + '-'.repeat(42 - code.length);
}
```
Проверено на десятках реальных примеров — паттерн стабильный.

Работает и для матчей, которых нет в `livematchids.json`/`schedule.json`
(годится как универсальный fallback по известному коду).

## 6. Разбор счёта

`competitiors[i].scores` — строка `"11,7,11,9,6"`, где каждое число — счёт
в одном сыгранном гейме этого игрока. Если матч закончился быстрее, чем за
максимум геймов (`matchConfig.bestOfXGames`), **оставшиеся геймы всё равно
присутствуют в строке как `0`** ("11,7,11,9,0" для матча, законченного за 4
гейма при best-of-5) — их нужно обрезать при отображении (не показывать
пустые "0-0" геймы), но НЕ обрезать при подсчёте выигранных сетов.

```js
function computeSets(scoresA, scoresB) {
  const setsA = scoresA.filter((v, i) => v > (scoresB[i] || 0)).length;
  const setsB = scoresB.filter((v, i) => v > (scoresA[i] || 0)).length;
  return { setsA, setsB };
}
function isDecided(setsA, setsB, bestOfXGames = 5) {
  const need = Math.ceil(bestOfXGames / 2);
  return setsA >= need || setsB >= need;
}
```

## 8. Общие грабли (чтобы не наступать повторно)

- Query-параметр `?q=...` — **чистый кэш-бастер**, сервер его не парсит
  как дату/фильтр (проверяли много вариантов формата — без разницы).
- Не полагайся на `Content-Length` заголовка как индикатор размера ответа —
  это сжатый (gzip) размер на проводе, не длина распакованного JSON.
- В долго открытой вкладке браузера конечный рендер может отличаться от
  того, что отдаёт `fetch()` из-за `localStorage`-кэша самого сайта
  (`event_schedule_v2_{eventId}` + `..._expiry`) — если сравниваешь свои
  данные с тем, что видно на сайте живьём, чисти `localStorage` или
  открывай в приватном окне.
